## 1. ES8311/ES7210 音频编解码与 OPUS-PCM 处理

### 1.1 服务端 OPUS-PCM 音频处理管线

**服务端（`xiaozhi-server`）** 的音频处理流程：

| 阶段 | 格式 | 说明 |
|------|------|------|
| ESP32 → 服务器 | **OPUS** | WebSocket 二进制传输 |
| 服务器内部 VAD/ASR | **PCM** | ASR Provider 解码后处理 |
| 服务器 → ESP32 | **OPUS** | 通过 `OpusEncoderUtils` 编码 |

核心配置在 `config.yaml`：

```yaml
xiaozhi:
  type: hello
  version: 1
  transport: websocket
  audio_params:
    format: opus
    sample_rate: 24000      # 采样率
    channels: 1             # 单声道
    frame_duration: 60      # 60ms 帧长
```

服务器端的 `OpusEncoderUtils`（位于 `core/utils/opus_encoder_utils.py`）负责将 TTS 输出的 PCM 编码为 OPUS 发回设备。ASR 接收端则通过各 Provider 将 OPUS 解码为 PCM 进行识别。

### 1.2 ES8311 + ES7210 硬件支持情况

**虾哥的 `xiaozhi-esp32` 固件已原生支持 ES8311（DAC 输出）+ ES7210（ADC 输入）组合**，通过 **`BoxAudioCodec`** 类实现。

已支持的开发板（均使用 ES8311 + ES7210 方案）：

| 开发板 | 音频方案 |
|--------|----------|
| ESP32-S3-Korvo2-V3 | ES8311 + ES7210 |
| ESP-Box / ESP-Box-3 | ES8311 + ES7210 |
| ESP-S3-LCD-EV-Board | ES8311 + ES7210 |
| Waveshare S3 Audio Board | ES8311 + ES7210 |
| M5Stack Tab5 | ES8388 + ES7210 |
| DF-K10 | ES8311 + ES7243E |
| ATK-DNESP32S3-BOX3 | ES8311 + ES7210 |

固件中的两种编解码器模式：

- **`BoxAudioCodec`**：ES8311（DAC 输出）+ ES7210（ADC 输入），适合有独立 ADC 的板子
- **`Es8311AudioCodec`**：ES8311 双工模式（内部 ADC + DAC），适合只有 ES8311 的板子

### 1.3 关于模拟麦克风的注意事项

> ⚠️ ES7210 是 **PDM 数字 MEMS 麦克风接口芯片**，原生设计用于连接数字 MEMS 硅麦，而非模拟驻极体麦克风。

如果你的模拟麦克风：
- **连接到 ES8311 的 ADC 输入** → 应使用 `Es8311AudioCodec`（双工模式）
- **连接到 ES7210** → 需要确认是否有模拟前端电路转接

### 1.4 兼容性总结

| 问题 | 答案 |
|------|------|
| 服务端 OPUS-PCM 管线能否处理？ | ✅ 可以，服务端对硬件 codec 透明，只关心 OPUS 格式 |
| 固件是否支持 ES8311 + ES7210？ | ✅ 支持，通过 `BoxAudioCodec` 已适配多款开发板 |
| 模拟麦克风是否兼容？ | ⚠️ 需确认硬件连接，ES7210 原生为数字 MEMS 麦设计 |

## 2. 语音控制工业设备总体方案

### 2.1 整体架构设计

当前项目已具备完整的基础框架，但工业设备控制与家居智能设备有本质区别，建议采用 **三层架构**：

```
┌─────────────────────────────────────────────────────────┐
│  语音输入层 (现有)                                        │
│  ESP32设备 → WebSocket/OPUS → xiaozhi-server             │
│  → ASR识别 → LLM意图理解 → Function Call                 │
├─────────────────────────────────────────────────────────┤
│  业务逻辑层 (新增插件)                                     │
│  plugins_func/functions/                                 │
│  ├── crane_control.py      # 塔机控制                     │
│  ├── gantry_control.py     # 龙门吊控制                   │
│  └── battery_car_control.py # 电瓶车控制                  │
├─────────────────────────────────────────────────────────┤
│  设备通信层 (需建设)                                       │
│  MQTT网关/MODBUS网关 → PLC/DTU/边缘控制器 → 物理设备       │
└─────────────────────────────────────────────────────────┘
```

### 2.2 涉及的通信协议

#### 项目已有并可复用的协议

| 协议 | 用途 | 现状 |
|------|------|------|
| **WebSocket** | ESP32 ↔ 服务器实时语音流 | ✅ 已实现 |
| **MQTT** | 通过 xiaozhi-mqtt-gateway 连接 | ✅ 已集成 |
| **UDP** | MQTT 网关辅助发现/数据通道 | ✅ 已集成 |
| **HTTP REST** | 调用第三方 API（如塔机数据） | ✅ 已实现（参考 `taji_auth.py`） |

#### 工业设备侧需增加的协议

| 协议 | 适用设备 | 说明 |
|------|----------|------|
| **Modbus RTU/TCP** | 塔机力矩限制器、PLC | 工业最通用的串行协议 |
| **CAN Bus** | 龙门吊变频器、电瓶车控制器 | 工程机械标配，抗干扰强 |
| **RS485** | 传感器、编码器、限位开关 | 长距离可靠传输 |
| **MQTT** | 边缘网关 ↔ 服务器 | 解耦设备层和业务层 |

| 设备 | 协议支持 | 适用场景 |
|------|----------|----------|
| **有人物联网 USR-G780** | Modbus RTU ↔ MQTT | 塔机/龙门吊串口设备上云 |
| **宏电 H7710** | 4G DTU + Modbus | 工业级，支持透明传输 |
| **ESP32 自建网关** | RS485 + WiFi/MQTT | 成本最低，可用 `xiaozhi-esp32` 改造 |

### 2.4 关键安全注意事项

| 风险 | 措施 |
|------|------|
| **误触发控制** | 必须增加二次确认："是否确认执行 XX 操作？" |
| **语音误识别** | 关键操作（急停除外）加声纹验证 + 操作码确认 |
| **权限控制** | 不同角色不同权限，操作员/安全员/管理员 |
| **急停保护** | 物理急停按钮优先级最高，语音控制不可绕过 |
| **工地网络不稳定** | DTU 必须支持离线缓存 + 断线重连 |
| **指令丢失/重复** | 消息ID去重 + ACK确认机制 |
| **延迟过高** | 关键指令设超时，超时自动进入安全状态 |
| **电磁干扰** | CAN/MODBUS 通信线加屏蔽、磁环 |
| **多设备防碰撞** | 塔机和龙门吊同场时需全局状态管理 |

## 3. Modbus 协议详解

### 3.1 协议本质

Modbus 是 1979 年由 Modicon（现施耐德电气）发布的**应用层串行通信协议**，核心思想：**一问一答的主从模式**。

### 3.2 两种物理层实现

```
Modbus RTU（串行）                  Modbus TCP（以太网）
══════════════════════              ══════════════════════
RS485 / RS232 物理层                TCP/IP 网络层
┌──────────┐                       ┌──────────┐
│  主站     │                       │  客户端   │
│ (PLC/PC) │                       │ (SCADA)  │
└────┬─────┘                       └────┬─────┘
     │ 一对多                             │ TCP 502端口
┌────┼────┬────┐                  ┌───────┼───────┐
▼    ▼    ▼    ▼                  ▼       ▼       ▼
从站1 从站2 从站3 从站4           服务器1  服务器2  服务器3
(最多247个从站)                   (IP:端口寻址)
```

| 特性 | Modbus RTU | Modbus TCP |
|------|-----------|------------|
| 物理介质 | RS485 双绞线（差分信号） | 以太网 RJ45 |
| 最大距离 | 1200m | 100m（可交换机延长） |
| 速率 | 9600~115200 bps | 10/100 Mbps |
| 帧校验 | CRC-16 | TCP 自带校验 |
| 地址范围 | 1~247 | IP:Port |
| 工地适用性 | ⭐⭐⭐⭐⭐ 主流 | ⭐⭐⭐ 需布线 |

### 3.3 四种寄存器表（数据模型）

PLC 和工控设备内部的数据被抽象为四种"寄存器表"：

```
┌─────────────────────────────────────────────────────────┐
│  PLC / 设备 内部                                          │
│                                                         │
│  线圈 (Coils)          离散输入 (Discrete Inputs)        │
│  地址: 0xxxx           地址: 1xxxx                       │
│  读写: R/W             读写: R(只读)                      │
│  类型: 1 bit (开关量)   类型: 1 bit (按钮/限位/传感器)     │
│  示例: 电机启停          示例: 限位开关状态                 │
│                                                         │
│  保持寄存器 (Holding)   输入寄存器 (Input Registers)       │
│  地址: 4xxxx           地址: 3xxxx                       │
│  读写: R/W             读写: R(只读)                      │
│  类型: 16 bit (模拟量)  类型: 16 bit (模拟量输入)           │
│  示例: 速度设定值        示例: 高度传感器读数               │
└─────────────────────────────────────────────────────────┘
```

> **记忆技巧**：1x/3x 是"只读的"（传感器输入），0x/4x 是"可写的"（控制输出）。工控中 90% 用的都是 **4xxxx 保持寄存器**。

### 3.4 常用功能码

| 功能码 | 名称 | 操作 | 示例场景 |
|--------|------|------|----------|
| **01** | 读线圈 | 读多个开关量输出 | 查询电机是否在运行 |
| **02** | 读离散输入 | 读多个开关量输入 | 读取限位开关状态 |
| **03** | 读保持寄存器 | 读多个16位寄存器 | 读取当前高度/重量 |
| **05** | 写单个线圈 | 写1个开关量 | 启动/停止电机 |
| **06** | 写单个寄存器 | 写1个16位值 | 设定目标速度 |
| **15** | 写多个线圈 | 批量写开关量 | 同时控制多个继电器 |
| **16** | 写多个寄存器 | 批量写16位值 | 设定速度+加速度参数 |

### 3.5 帧结构示例（Modbus RTU）

```
主站发送：读保持寄存器（功能码 03），从地址 40001 开始读 2 个寄存器
┌──────┬──────┬──────────┬──────────┬────────────┐
│ 从站地址│ 功能码│ 起始地址   │ 寄存器数量 │ CRC校验     │
│ 01   │ 03  │ 00 00   │ 00 02   │ C4 0B     │
│ 1B   │ 1B  │ 2B      │ 2B      │ 2B        │
└──────┴──────┴──────────┴──────────┴────────────┘

从站应答：
┌──────┬──────┬──────┬────────────────────┬────────────┐
│ 01   │ 03  │ 04  │ 00 6C  00 18       │ 7B 8D     │
│ 地址  │ 功能码│ 字节数│ 108(高度) 24(速度) │ CRC        │
└──────┴──────┴──────┴────────────────────┴────────────┘
解读：塔机当前高度 = 0x006C = 108米，速度 = 0x0018 = 24（单位视设备而定）
```

### 3.6 塔机场景寄存器映射示例

```
┌──────────┬──────────┬────────┬─────────────────────────┐
│ 地址     │ 类型     │ 方向   │ 含义                    │
├──────────┼──────────┼────────┼─────────────────────────┤
│ 40001    │ 线圈     │ W      │ 起升启动 = 1, 停止 = 0   │
│ 40002    │ 线圈     │ W      │ 下降启动                 │
│ 40003    │ 线圈     │ W      │ 回转左转                 │
│ 40004    │ 线圈     │ W      │ 回转右转                 │
│ 40005    │ 线圈     │ W      │ 急停（常闭，断开=急停）    │
│ 40010    │ 保持寄存器│ R      │ 当前高度 (dm)            │
│ 40011    │ 保持寄存器│ R      │ 当前幅度 (cm)            │
│ 40012    │ 保持寄存器│ R      │ 当前吊重 (kg)            │
│ 40013    │ 保持寄存器│ R      │ 当前力矩百分比 (%)        │
│ 40014    │ 保持寄存器│ R      │ 风速 (0.1 m/s)           │
│ 40020    │ 保持寄存器│ W      │ 目标高度设定值            │
└──────────┴──────────┴────────┴─────────────────────────┘
```

## 4. CAN 协议详解

### 4.1 协议本质

CAN（Controller Area Network）是 1986 年由 Bosch 为汽车行业开发的**多主总线通信协议**。核心区别：**没有主从之分，任何节点都可以主动发送**。具有高实时性、强抗干扰能力，已成为工程机械（塔机、龙门吊、盾构机）和汽车的标配协议。

### 4.2 Modbus vs CAN 对比

```
        Modbus（主从）                    CAN（多主）
        ════════════════                  ════════════════
        
        主站                              节点A   节点B   节点C
         │                                │      │      │
    ┌────┼────┬────┐                       └──┬───┴──┬───┘
    ▼    ▼    ▼    ▼                          │      │
   从站  从站  从站  从站                   ════╧══════╧════  CAN总线
                                               │
   "点名回答问题"                          "抢到总线就发言"
   必须主站发起                            谁都可以主动上报
```

| 特性 | Modbus RTU | CAN Bus |
|------|-----------|---------|
| 通信模式 | 主从（单主） | 多主（任意节点可发） |
| 最高速率 | 115.2 Kbps | 1 Mbps (CAN 2.0), 8 Mbps (CAN FD) |
| 实时性 | 轮询延迟大 | 微秒级，硬实时 |
| 错误检测 | CRC-16 | CRC-15 + ACK + 位错误 + 填充错误 + 帧检查 (5重) |
| 优先级 | 无，靠轮询顺序 | 硬件仲裁（ID越小优先级越高） |
| 抗干扰 | 一般（差分信号） | 极强（差分 + 错误计数 + 自动隔离故障节点） |
| 最大节点数 | 247（实际32） | 理论无限制，实际110+ |
| 帧长度 | 最长256字节 | 8字节 (CAN 2.0), 64字节 (CAN FD) |
| 工地适用 | 传感器/PLC | 发动机ECU/变频器/控制器 |

### 4.3 帧结构（CAN 2.0B 扩展帧）

```
┌──────┬──────────┬────┬────┬────────┬───────┬──────┬──────┬────┬──────┐
│ SOF  │ 仲裁域   │IDE │保留 │ DLC   │数据域  │ CRC  │ ACK  │EOF │ 帧间 │
│ 1bit │ 29bit ID │1bit│1bit│ 4bit  │0~64bit│15bit │ 2bit │7bit│ 3bit │
└──────┴──────────┴────┴────┴───────┴───────┴──────┴──────┴────┴──────┘
                    ↑                       ↑
               ID决定优先级            实际负载8字节(标准帧)
```

### 4.4 仲裁机制（CAN 最核心的设计）

CAN 总线的仲裁是**非破坏性逐位仲裁**，这是它实现硬实时的关键：

```
时间轴 →
节点A ID: 0x1A6 = 0001 1010 0110
节点B ID: 0x1A3 = 0001 1010 0011
节点C ID: 0x1F0 = 0001 1111 0000
                   ││││ ││││ ││││
总线电平:  ────────┘││││ ││││ ││││  ← 逐位比较
                    ↓↓↓↓
              节点B的ID最小(0x1A3)，仲裁胜出，立即发送
              节点A和C检测到自己发1却读到0，自动退出发送，转为监听

关键：仲裁过程不破坏正在传输的数据！高优先级节点零延迟抢占。
```

> **工地应用的核心价值**：急停信号的 CAN ID 设为最高优先级（如 0x001），一旦发送，所有其他通信立即让路。

### 4.5 工程机械中的 CAN 应用实例

```
塔机控制系统 CAN 网络
═══════════════════════════════════════════════════════
                     CAN Bus (250 Kbps)
    ┌────────┬────────┬────────┬────────┬────────┐
    │        │        │        │        │        │
    ▼        ▼        ▼        ▼        ▼        ▼
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│PLC主控│ │变频器│ │力矩   │ │风速仪│ │编码器│ │显示屏│
│控制器 │ │(起升)│ │限制器│ │      │ │(高度)│ │(HMI) │
│ID:0x10│ │0x20  │ │0x30  │ │0x40  │ │0x50  │ │0x60  │
└──────┘ └──────┘ └──────┘ └──────┘ └──────┘ └──────┘

CAN ID 分配示例：
  0x101 - 起升电机转速指令（PLC → 变频器）
  0x102 - 起升电机实际转速反馈（变频器 → PLC）
  0x201 - 当前吊重数据（力矩限制器 → 显示屏）
  0x202 - 力矩超载报警（力矩限制器 → PLC，高优先级）
  0x001 - 紧急停止（任意节点 → 全部节点，最高优先级）
  0x301 - 当前高度（编码器 → PLC/显示屏）
```

## 5. 西门子 IOT2050 边缘网关

### 5.1 设备本质

**SIMATIC IOT2050** 是西门子推出的**工业级边缘计算网关**，可理解为一台运行 Debian Linux 的工控小电脑。它位于 OT（操作技术/设备层）和 IT（信息技术/云端层）之间，是工业 4.0 的核心桥梁。

```
┌────────────────────────────────────────────────────────────┐
```

### 5.3 IOT2050 上的核心代码实现

#### Modbus ↔ MQTT 桥接脚本

```python
# iot2050_bridge.py —— 运行在 IOT2050 上
import paho.mqtt.client as mqtt
from pymodbus.client import ModbusSerialClient
import json
import threading
import time

# ── Modbus 寄存器映射表 ──
REGISTER_MAP = {
    "塔机1": {
        "port": "/dev/ttyUSB0",  # RS485 口1
        "slave_id": 1,
        "registers": {
            "lift_start":    {"addr": 0, "type": "coil"},       # 40001
            "lower_start":   {"addr": 1, "type": "coil"},       # 40002
            "emergency":     {"addr": 4, "type": "coil"},       # 40005
            "target_height": {"addr": 19, "type": "holding"},   # 40020
            "current_height":{"addr": 9, "type": "holding"},    # 40010
            "current_weight":{"addr": 10, "type": "holding"},   # 40011
            "wind_speed":    {"addr": 13, "type": "holding"},   # 40014
        }
    },
    "塔机2": { "port": "/dev/ttyUSB1", "slave_id": 2 },
    "龙门吊1": { "port": "/dev/ttyUSB2", "slave_id": 3 },
}

# ── MQTT → Modbus 指令下发 ──
def on_mqtt_message(client, userdata, msg):
    """收到小智服务器下发的控制指令"""
    parts = msg.topic.split("/")
    device = parts[1]      # e.g. "塔机1"
    command = parts[3]     # e.g. "lift"

    config = REGISTER_MAP[device]
    modbus = ModbusSerialClient(port=config["port"], baudrate=9600)

    if command == "lift":
        payload = json.loads(msg.payload)
        target_height = payload["target"]
        modbus.write_register(
            config["registers"]["target_height"]["addr"],
            target_height, slave=config["slave_id"]
        )
        modbus.write_coil(
            config["registers"]["lift_start"]["addr"],
            True, slave=config["slave_id"]
        )
        client.publish(
            f"crane/{device}/status",
            json.dumps({"action": "lifting", "target": target_height})
        )

    elif command == "emergency_stop":
        modbus.write_coil(
            config["registers"]["emergency"]["addr"],
            True, slave=config["slave_id"]
        )
        client.publish(
            f"crane/{device}/status",
            json.dumps({"action": "emergency_stop", "status": "stopped"})
        )

# ── Modbus → MQTT 状态上报（轮询） ──
def status_polling_loop():
    """定时读取设备状态，上报给小智服务器"""
    while True:
        for device_name, config in REGISTER_MAP.items():
            modbus = ModbusSerialClient(port=config["port"], baudrate=9600)
            modbus.connect()
            try:
                height = modbus.read_holding_registers(
                    config["registers"]["current_height"]["addr"],
                    1, slave=config["slave_id"]
                ).registers[0]
                weight = modbus.read_holding_registers(
                    config["registers"]["current_weight"]["addr"],
                    1, slave=config["slave_id"]
                ).registers[0]

                mqtt_client.publish(
                    f"crane/{device_name}/telemetry",
                    json.dumps({
                        "height_m": height / 10,
                        "weight_kg": weight,
                        "timestamp": int(time.time())
                    })
                )
            except Exception as e:
                print(f"[ERROR] {device_name} 读取失败: {e}")
            modbus.close()
        time.sleep(2)

mqtt_client = mqtt.Client()
mqtt_client.on_message = on_mqtt_message
mqtt_client.connect("xiaozhi-server-ip", 1883)
mqtt_client.subscribe("crane/+/command/#")

threading.Thread(target=status_polling_loop, daemon=True).start()
mqtt_client.loop_forever()
```

## 6. 4G DTU 与 Modbus RTU/CAN Bus 的关系

### 6.1 核心概念：DTU 是"透明管道"

```
                   4G DTU 的本质
            ════════════════════════════
            
              RS485 端                   云端
            ┌─────────┐               ┌──────────┐
            │ Modbus  │   4G DTU      │ 虚拟串口   │
   PLC ────→│ RTU 帧  │═══════════════→│ 收到完全  │
            │ 01 03.. │  透明透传       │ 相同的帧  │
            └─────────┘  不解析内容    └──────────┘
            
            类比：DTU = 一根很长很长的 RS485 延长线
            它把串口信号打包成 4G 数据包，到对端再还原
            中间的 DTU 完全不懂 Modbus 协议在说什么
```

**一句话理解**：4G DTU 像一根"无线延长线"，把工地 RS485 串口延伸到远端服务器的虚拟串口上，Modbus RTU 的帧在传输过程中保持不变。

### 6.2 三种通信架构对比

#### 架构A：纯 DTU 透明传输

```
  龙门吊 PLC                      远端服务器
  ┌──────────┐                   ┌──────────────────┐
  │ RS485口  │──RS485线──┐        │ 虚拟串口软件       │
  │ Modbus   │          │        │ (如 USR-VCOM)     │
  │ RTU 主站 │      ┌───▼───┐    │       │           │
  └──────────┘      │ 4G DTU│════│ pymodbus 轮询     │
                    │(从站) │    │       │           │
                    └───────┘    │ xiaozhi-server    │
                                 └──────────────────┘
```

- **优点**：部署极简，DTU配好就能用
- **致命缺陷**：
  - ❌ 每个轮询周期都有 4G 延迟（50-200ms）→ 累积延迟巨大
  - ❌ 网络断线时 Modbus 超时，整个通信链路崩溃
  - ❌ 无法实现事件主动上报（只能被动轮询）
  - ❌ 服务器压力大（需轮询所有寄存器）

#### 架构B：边缘网关 + 协议转换（推荐 ⭐⭐⭐⭐⭐）

```
  龙门吊 PLC                  边缘网关               远端服务器
  ┌──────────┐   RS485    ┌──────────────┐   MQTT  ┌──────────┐
  │ RS485口  │───────────→│ IOT2050/     │════════→│ EMQX     │
  │ Modbus   │  本地轮询   │ 边缘网关      │  4G/WiFi│ Broker   │
  │ RTU 从站 │←───────────│              │←════════│          │
  └──────────┘  极低延迟   │ • 本地轮询PLC │ JSON    │ xiaozhi- │
                          │ • 协议转换    │  主动   │ server   │
                          │ • 本地缓存    │  上报   │          │
                          │ • 断网续传    │         └──────────┘
                          └──────────────┘
```

- **优点**：
  - ✅ RS485 通信在本地完成（< 1ms延迟），无 4G 轮询开销
  - ✅ 边缘网关主动上报状态变化（事件驱动，非轮询）
  - ✅ 断网时本地缓存数据，恢复后补传
  - ✅ 可在边缘侧做本地安全逻辑（即使断网也能急停）
  - ✅ 服务器只需订阅 MQTT 主题，压力极小

#### 架构C：4G DTU + 本地主站（折中方案）

```
  龙门吊 PLC           本地工控机/树莓派          远端服务器
  ┌──────────┐ RS485 ┌──────────────┐  MQTT  ┌──────────┐
  │ Modbus   │──────→│ 本地主站      │═══════→│ xiaozhi- │
  │ RTU 从站 │       │ (Python轮询)  │  4G    │ server   │
  └──────────┘       │              │   上报  └──────────┘
                     │ DTU只做网络  │
                     │ 不参与协议    │
                     └──────────────┘
```

### 6.3 4G DTU 能否直连 CAN Bus？

> ❌ **不能！** CAN Bus ≠ RS485，物理层不兼容。

```
         CAN Bus ≠ RS485，不能直接接 DTU！

         ┌──────────────────────────────────────────┐
         │  CAN Bus 特性               RS485 特性    │
         ├──────────────────────────────────────────┤
         │  多主（任意节点可主动发）   单主（主站轮询）│
         │  短帧（8/64字节）          长帧（256字节）  │
         │  硬件仲裁 + 优先级          无优先级        │
         │  差分信号(CANH/CANL)       差分信号(A/B)   │
         │  不可直接互转！             物理层不同！    │
         └──────────────────────────────────────────┘
```

如果龙门吊 PLC 只提供 CAN 接口，需要：

**方案1：CAN → Modbus RTU 网关（如广成 GCAN-212）**

```
┌──────┐   CAN    ┌──────────┐  RS485  ┌──────┐
│ PLC  │─────────→│ CAN→Modbus│────────→│ DTU  │→ 4G
│ CAN  │          │ 网关      │ Modbus  │      │
└──────┘          └──────────┘  RTU    └──────┘
```

**方案2：直接用带 CAN 接口的边缘网关**

```
┌──────┐   CAN    ┌──────────┐  MQTT   ┌──────────┐
│ PLC  │─────────→│ 边缘网关  │═══════→│ 服务器    │
│ CAN  │          │ + CAN模块 │  4G    │          │
└──────┘          └──────────┘         └──────────┘
```

```
  └─────────────────────────────────────────────────────────┘

  层3：逻辑互锁（防冲突指令）
  ┌─────────────────────────────────────────────────────────┐
  │ 边缘网关本地执行：                                         │
  │   ├── 大车前进时拒绝大车后退指令                            │
  │   ├── 起升上限位触发时拒绝继续上升                           │
  │   ├── 超载时拒绝任何起升动作                                │
  │   ├── 风速 > 6级时拒绝所有大车/起升动作                      │
  │   └── 两台龙门吊间距 < 安全距离时双向锁定                    │
  └─────────────────────────────────────────────────────────┘

  层4：通信监护（防断网失控）
  ┌─────────────────────────────────────────────────────────┐
  │ 心跳机制：边缘网关每 500ms 发一次心跳                        │
  │                                                          │
  │ 如果连续 3 次（1.5秒）未收到心跳：                          │
  │   边缘网关本地触发 → 自动停止所有动作 → 本地声光报警          │
  │                                                          │
  │ 如果连续 10 次（5秒）未收到心跳：                           │
  │   触发紧急制动 → 变频器自由停车 → 抱闸制动                    │
  └─────────────────────────────────────────────────────────┘

  层5：物理安全（不可绕过）
  ┌─────────────────────────────────────────────────────────┐
  │  物理急停按钮 ← 最高优先级，独立于所有电子系统              │
  │  操纵杆物理挡位 ← 操纵杆与语音 OR 逻辑，任意一方可控制      │
  │  限位开关 ← 硬接线，不经过 PLC 软件逻辑                     │
  │  过载保护 ← 力矩限制器独立回路                              │
  └─────────────────────────────────────────────────────────┘
```

### 7.5 实施路径

```
Phase 1：现场调研（2天）
├── 确认龙门吊 PLC 型号和通信接口（RS485 / CAN / 以太网）
├── 确认 PLC 程序是否可修改（新增远程控制数据块）
├── 获取 Modbus 寄存器地址表
├── 测试 4G 信号覆盖情况
└── 确认供电和安装位置

Phase 2：边缘网关搭建（3天）
├── IOT2050 部署 + 4G 模块调试
├── Modbus RTU 通信调试（本地直连 PLC 测试）
├── MQTT Bridge 开发 + 与服务器联调
├── 本地安全看门狗 + 心跳机制
└── 装箱 + 防护 + 上电测试

Phase 3：服务端插件开发（2天）
├── 龙门吊控制 Function Call 插件
├── 声纹确认 + 二次确认机制
├── 设备影子 + 指令队列
└── 智控台配置（智能体 → 功能管理）

Phase 4：联调测试（3天）
├── 空载测试（无吊物）
├── 带载测试（逐步加重）
├── 异常场景测试（断网/断电/超载/限位触发）
├── 安全审查（第三方监理确认）
└── 操作员培训

Phase 5：试运行（1周）
├── 旁路监控模式（语音可控制但人工在旁监督）
├── 数据采集 + 稳定性评估
└── 正式切换
```
